# Change, Release & Defect Management

## Build, install & promotion management

| Activity | What it does |
|---|---|
| **Release Management** | Plan, schedule, build, test & deploy versions. Activities: planning → build verification → packaging & deployment → **version tagging** → post-release review. Keep **release notes** & rollback readiness. |
| **Build Management** | Compile source into deployable artifacts **consistently & reproducibly**: compile/link → dependency resolution → **incremental builds** → CI → artifact archiving. |
| **Install Management** | Package & deploy into the operational environment (consistent, verified, **reversible**): installer creation → pre-install checks → execution → post-install validation → **rollback**. |
| **Promotion Management** | Control how software moves **Dev → QA → UAT → Staging → Production** by defined criteria (tests pass, QA approval, code review). Enforce **promotion gates**; lock the production branch. |

> [!INTUITION]
> **Promotion** is the controlled escalation of a build through environments. Each gate (Dev→QA→Staging→Prod) demands evidence — tests passed, approvals signed — so only **trusted** builds reach production.

## Change management

> [!NOTE]
> **Change Management** is the formal process of requesting, evaluating, approving, implementing and reviewing changes — ensuring evolution is **managed, cost-effective and prioritized**, with full auditability.

**The process (overseen by the CCB):**
```
Change Request (CR) → validity check (real? duplicate?) → impact & cost analysis
   → CCB selects (by priority/urgency) → implement → test → verify & close
```

**Change Request Form fields:** Project, CR Number, Requested Change, Requester, Date, Analyzer, Associated Components, **CCB Decision**. *(e.g. CR #2302 "show visual status in applicant list" — simple colour change, no DB change, medium priority → approved for Release 1.2, ~2 hours, QA required.)*

> [!EXAM]
> **Five factors the CCB weighs** before approving a change: **(1)** consequences of **not** making it · **(2)** the benefits · **(3)** the number of users affected · **(4)** the cost (dev, test, docs, training) · **(5)** fit with the release cycle.

**Derivation history** — an audit trail per component (Version, Modifier, Date, Change, Reason), auto-generated by the VCS; essential for debugging, compliance and rollback.

> [!NOTE]
> **Change management in Agile** is customer-centric and lightweight: customers propose changes, evaluated against the next sprint/backlog; **refactoring** is a **core practice, not overhead**.

## Defect (Bug) management

> [!NOTE]
> **Defect management** systematically records, tracks, resolves and verifies defects, with full traceability and severity-based prioritization.

**Defect lifecycle:**
```
Detection → Logging (steps, severity, screenshots) → Triage → Assignment
   → Fixing & Testing → Closure   (or → Reopened if the fix fails)
```
States: **New → (Rejected / Duplicate / Deferred) / Assigned → In Progress → Fixed → Closed / Reopened.**

> [!TRAP]
> Triage can route a logged bug to **Rejected** (not reproducible / expected behaviour), **Duplicate**, or **Deferred** (valid but low priority) — not every logged "bug" becomes a fix. *(Classic question: Word suggesting "teh"→"the" is an **improvement request, not a bug** — the software works correctly but can be enhanced.)*

**Metrics:** track **MTTR** (Mean Time To Resolve) and **Reopen Rate**; always **link fixes to commits and releases**.
