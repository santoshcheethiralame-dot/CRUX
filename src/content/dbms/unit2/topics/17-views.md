# Views

> [!EXAM]
> - **A view in MySQL is a virtual table.**
> - **It doesn't store actual data by itself** but instead **stores a query that pulls data from one or more tables (or even other views)**.
> - Primarily used to **hide complex queries** and simplify them into a convenient table-like storage.
> - Since this is stored, we can **reuse these views and avoid writing SQL queries multiple times**.
> - Generally used when we want a table for a **specific use case**, or want to **assign roles**.

> [!NOTE]
> **We define a view in SQL by using the `CREATE VIEW` command:**
>
> ```sql
> CREATE VIEW view1 AS <query expression>;
> ```
>
> where `<query expression>` is **any legal query expression**, and `view1` is the view name.
>
> To create a view we can **select fields from one or more tables** present in the database, and a view can have **specific rows based on a condition, or all the rows of a table**.

> [!INTUITION]
> "Virtual table" is precise: the view **stores the query text, not the rows**. Every time you query the view, the stored query runs against the current base tables.
>
> Two consequences follow, and they are the source of most exam questions:
>
> - **A view is always up to date.** Insert into the base table and the view reflects it immediately, because there is no copy to go stale.
> - **A view saves no query time.** Querying a view costs whatever the underlying query costs. Views buy **readability, reuse and security** — never speed. (A *materialized* view, which does store rows, is a different feature.)

## When is a view updatable?

> [!EXAM]
> **We can create a view from one table or using joins with multiple tables — but if you create a multi-join view, then only read operations are allowed.**
>
> **A view is updatable (CRUD operations) only if these criteria are met:**
> 1. The view is created **on a single table only**
> 2. Does **not contain aggregate functions** like `SUM`, `MAX`, `COUNT` etc.
> 3. Does **not contain `DISTINCT`, `GROUP BY`, `HAVING` or `UNION`**
> 4. Does **not have joins or subqueries**
> 5. The query is **not recursive** in nature

> [!INTUITION]
> Do not memorise five arbitrary rules — they are all **one rule wearing five hats**:
>
> > **An update to a view is only meaningful if each view row traces back to exactly one base-table row.**
>
> Check each condition against that:
> - **Aggregates** — a view row is a *summary of many rows*. What should "set the average salary to 50000" do to the individuals? There is no answer.
> - **`DISTINCT` / `GROUP BY`** — again, one view row stands for several base rows.
> - **`UNION`** — a row could have come from either branch; which table do you write to?
> - **Joins** — a view row is *two* base rows stitched together, so an update is ambiguous about which one to modify.
> - **Recursion** — a row may be generated by iteration and correspond to no single stored row at all.
>
> **Every condition is the same demand: an unambiguous one-to-one path back to a stored row.** Derive the list from that and you cannot forget an item.

## Updates propagate to the base table

The deck demonstrates CRUD on a view over a single `Authors` table:

```sql
CREATE VIEW experienced_authors AS
SELECT * FROM authors
WHERE  age >= 30 AND Bio LIKE '%Expert%';
```

Of the nine authors in the base table, exactly three satisfy both conditions:

| Author_ID | Name | Age | Bio |
|---|---|---|---|
| A001 | Alice Johnson | 35 | Expert in AI and ML |
| A006 | Frank Martin | 45 | Expert in Computer Vision |
| A009 | Ivy Scott | 34 | Data Engineering Expert |

> [!TRAP]
> Check who is **excluded**, because the two conditions do different work. **Carol White (28)** and **Henry Wilson (27)** are researchers but too young. **Bob Smith (40, "Data Scientist")** and **Eve Davis (32, "Cloud Computing Specialist")** are old enough but their bios never say *Expert*.
>
> And note `Bio LIKE '%Expert%'` is a **substring** match, not a word match — it catches *"Data Engineering **Expert**"* with the word at the end just as happily as at the start. It would equally match a bio reading *"no Expertise in..."*. This is precisely the word-boundary weakness that **Full-Text Search** exists to fix.

After the insert, update and delete, the view holds Alice (now 40), Frank, and the newly added **John Wick (52, "Expert in Pencils")** — who qualifies because he meets both conditions.

> [!EXAM]
> **All the changes made to the view are also reflected on the original tables.**
>
> In the demonstration: **Alice's age was changed to 40, John Wick was added, and Ivy Scott was removed — from the `Authors` table itself.**

> [!TRAP]
> A view is **not a copy or a sandbox**. Writing through it writes through to real data, permanently.
>
> There is a sharper hazard here too. Insert a row through the "experts" view that does **not** satisfy the view's own condition — say an author aged 22 — and the row **lands in the base table but vanishes from the view**. It was written successfully and is simply invisible through the window you wrote it through.
>
> (The standard guard is `WITH CHECK OPTION`, which rejects such inserts.)

## Views over the company database

**Example 1:** A view listing each employee's full name, their department name, and the total number of projects they work on:

```sql
CREATE VIEW EmpProjSummary AS
SELECT E.Fname, E.Lname, D.Dname, COUNT(W.Pno) AS ProjectCount
FROM   EMPLOYEE E JOIN DEPARTMENT D ON E.Dno = D.Dnumber
       JOIN WORKS_ON W ON E.Ssn = W.Essn
GROUP BY E.Ssn, E.Fname, E.Lname, D.Dname;
```

Then query it like an ordinary table:

```sql
SELECT Fname, Lname, Dname, ProjectCount
FROM   EmpProjSummary WHERE ProjectCount >= 3;
```

**Example 2:** Employees with the number of dependents they have, then those with more than 2:

```sql
CREATE VIEW EmpDependentCount AS
SELECT E.Fname, E.Lname, COUNT(Dp.Dependent_name) AS NumDependents
FROM   EMPLOYEE E
LEFT JOIN DEPENDENT Dp ON E.Ssn = Dp.Essn
GROUP BY E.Ssn, E.Fname, E.Lname;
```

```sql
SELECT * FROM EmpDependentCount WHERE NumDependents > 2;
```

> [!EXAM]
> **Both of these views are read-only** — each has joins *and* aggregation *and* `GROUP BY`, failing three of the five updatability conditions. That is the intended reading of the examples.
>
> Note again the `LEFT JOIN` + `COUNT(column)` pairing in Example 2, so that employees with **zero** dependents appear with a count of 0 rather than being dropped.

## Advantages

> [!EXAM]
> | Advantage | Detail |
> |---|---|
> | **Complexity** | Views help **reduce complexity**. Different views can be created on the **same base table for different users** |
> | **Security** | Increases security by **excluding sensitive information** from the view |
> | **Query simplicity** | A view can **draw data from several different tables and present it as a single table** |
> | **Consistency** | Presents a **consistent, unchanged image of the structure of the database**. Views can **rename columns without affecting the base table** |
> | **Data integrity** | If data is accessed and entered through a view, the DBMS can **automatically check that it meets the specified integrity constraints** |
> | **Storage capacity** | Views **take very little space to store** |
> | **Logical data independence** | Views can make the application and the database tables **independent to a certain extent** |

> [!INTUITION]
> **Security** and **logical data independence** are the two that matter most, and they connect back to Unit 1.
>
> **Security by subtraction:** grant a clerk access to a view of `EMPLOYEE` that omits `Salary`, and revoke their access to the base table. They can do their job and *cannot* see salaries — the restriction is structural, not a matter of trust. This is exactly why the deck pairs views with users and roles.

> [!TRAP]
> **The deck's own demo view does the opposite of what the Security advantage claims** — worth noticing, because it is the mistake the advantage is warning against.
>
> `experienced_authors` is defined as **`SELECT *`**, and the `Authors` table carries a **`Password`** column storing values in plaintext (`password123`, `password987`, …). So the view **republishes every password** to anyone granted access to it.
>
> Two lessons. First, a view only excludes sensitive information **if you actually name the columns** — `SELECT *` in a view definition forfeits the entire security benefit, and it also means the view silently acquires any column added to the base table later. Second, the plaintext passwords are a schema defect in their own right; real systems store a salted hash and never a recoverable password.
>
> If an exam asks you to write a view "for security," **list the columns explicitly.**
>
> **Logical data independence** is the middle level of the **three-schema architecture** from Unit 1. A view *is* an external schema. Split a table in two, keep a view with the old shape, and every application written against that view keeps working — the conceptual schema changed and the external schema did not.

## Disadvantages

> [!EXAM]
> - You **cannot `INSERT`** if the base table has any **NOT NULL columns that do not appear in the view**.
> - You **cannot `INSERT` or `UPDATE`** if any of the referenced columns contain **group functions or columns defined by an expression**.
> - You **can't execute `INSERT`, `UPDATE`, `DELETE`** on a view if the **`WITH READ ONLY`** option is enabled.
> - You **can't create a view using temporary tables**.
> - You **cannot `INSERT`, `UPDATE` or `DELETE`** if the view contains **`GROUP BY`, `DISTINCT`, or a reference to a pseudo column `row_num`**.
> - You **can't pass parameters** to SQL Server views.
> - You **can't associate rules and defaults** with views.

> [!INTUITION]
> The first bullet is the subtlest and worth understanding rather than memorising. If the base table has a `NOT NULL` column that the view does not expose, an insert through the view **cannot supply a value for it** — the column is invisible from where you are standing. The base table would reject a NULL, so the insert cannot succeed at all.
>
> Note also **"you can't pass parameters to views"**: a view is a *fixed* query, not a function. If you need `CREATE VIEW EmployeesInDept(5)`, you actually need a **stored function or procedure** — the topics that follow.

## Views vs CTEs

> [!EXAM]
> | Feature | Views | CTEs |
> |---|---|---|
> | **Definition** | A **virtual table stored in the database**, defined by a query | A **temporary result set defined within a query** using `WITH` |
> | **Persistence** | **Persisted in the database schema until explicitly dropped** | **Exists only for the duration of the query execution** |
> | **Reusability** | Can be **reused across multiple queries** once created | Can only be used **inside the single query where it is defined** |
> | **Scope** | **Global** (available to all users with permissions) | **Local** (visible only within that query) |
> | **Complexity handling** | Good for **hiding complex joins, filters and calculations for repeated use** | Good for **breaking down complex queries into readable parts** (step-by-step) |
> | **Updatability** | **Some views are updatable** (single table, no aggregations) | **CTEs are not updatable** — they're just temporary results |
> | **Syntax** | `CREATE VIEW view_name AS <query>;` then `SELECT * FROM view_name;` | `WITH cte_name AS (<query>) SELECT * FROM cte_name;` |

> [!INTUITION]
> One line separates them: **persistence and scope.** A view is a **schema object** — created once, visible to everyone with permission, surviving until dropped. A CTE is a **local name** that exists for one statement and disappears.
>
> The decision rule follows directly: **will more than one query need this?** If yes, a view. If it is scaffolding for one complex query, a CTE. And if you need recursion, only a CTE can do it.
